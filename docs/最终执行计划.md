# Android UWB 防丢器最终执行计划

## 1. 目标

在 Samsung S23 Ultra 与 DWM3001CDK 之间实现一套可演示的 UWB 防丢器闭环：

1. 手机通过 BLE 扫描并连接 DWM3001CDK。
2. 手机作为 Android UWB Controller 创建 UWB session。
3. 手机通过 BLE-OOB 把 session 参数发送给开发板。
4. DWM3001CDK 作为 FiRa Controlee/Responder 启动 UWB。
5. 手机通过 AndroidX UWB 获取距离和方位角。
6. App 用距离、方向箭头、震动反馈完成寻物演示。

第一阶段以“真实测距闭环”为最高优先级，不先追求完整标准化 UCI over BLE、蜂鸣器、复杂 UI 或多设备管理。

## 2. 设备与约束

手机端：
- Samsung S23 Ultra
- 需要开启系统 UWB、定位、附近设备权限
- App 使用 AndroidX UWB

板端：
- Qorvo DWM3001CDK
- nRF52833 + DW3000
- 以 QANI 工程为固件基础，因为 QANI 已包含 BLE、SoftDevice、QNIS、FiRa、uwbmac、DW3000 驱动

关键约束：
- 官方 QANI 使用 Apple NIQ 协议，不适合直接对接 Android。
- Android App 可以任意重构，因此 App 侧按固件可实现路径调整。
- 第一版保留 QNIS BLE 通道，避免一开始引入未确认的 FiRa BLE Service UUID 或完整 UCI over GATT。

## 3. 总体技术路线

采用“QANI 固件骨架 + 自定义 Android OOB 协议 + AndroidX UWB”的路线。

### 3.1 Android 端基线

Android App 端以 Google 官方 `Android Connectivity Samples - UwbRanging` 为参考基线：

```text
https://github.com/android/connectivity-samples/tree/main/UwbRanging
```

该 sample 的 README 说明：

- 它展示 Android UWB Jetpack library 的基本能力。
- UWB 本身没有原生设备发现机制，必须提供 OOB 机制。
- Google sample 使用 Nearby Connections 作为 OOB，但 BLE、Wi-Fi 等其它无线协议也可以承担 OOB。
- sample 的原始前提是两台支持 UWB 的 Android 手机；本项目把其中的 Controlee 侧替换为 DWM3001CDK。

因此，本项目对 Google sample 的使用方式是：

1. App 的 UWB session 生命周期、Controller/Controlee 角色、`UwbManager` 调用、ranging result 处理，尽量与 Google sample 保持一致。
2. App 的 OOB 语义与 Google sample 对齐，即交换 session id、address、complex channel、STS/key info 等 UWB 参数。
3. OOB 传输介质从 Google sample 的 Nearby Connections 替换为 DWM3001CDK 已支持的 BLE QNIS。
4. 不直接依赖 Google sample 的两机 Android UI 和 Nearby Connections 代码，因为我们的对端不是 Android 手机，而是 DWM3001CDK 固件。

换句话说：**Android UWB 流程跟 Google sample，BLE-OOB 编码和板端启动逻辑按 DWM3001CDK 适配。**

BLE 只作为 OOB 参数通道：
- App 扫描 QNIS Service。
- App 连接 QNIS RX/TX。
- App 写入自定义 Android OOB START_SESSION 包。
- 板端解析后返回 ACK 和启动诊断。

UWB 测距由 Android 原生 UWB 完成：
- App 使用 `UwbManager.controllerSessionScope()` 获取本机 UWB 参数。
- App 根据板端地址构造 `RangingParameters`。
- App 收集 `RangingResultPosition`，提取 distance 和 azimuth。

板端只负责按 OOB 参数启动 FiRa responder：
- 解析 sessionId、short address、channel、preamble、STS、key info。
- 映射到 Qorvo `fira_device_configure_t` 或等价 FiRa 配置。
- 启动 uwbmac / FiRa session。

## 4. 固件执行计划

### 4.1 新建 AndroidRangingTag 工程

新建：

```text
Projects/FreeRTOS/AndroidRangingTag/
```

以 `Projects/FreeRTOS/QANI/` 为模板复制 DWM3001CDK 目标：

```text
Projects/FreeRTOS/AndroidRangingTag/Common/
Projects/FreeRTOS/AndroidRangingTag/DWM3001CDK/
```

保留：
- FreeRTOS
- Nordic BSP
- SoftDevice S113
- BLE QNIS
- FiRa
- UWB stack
- DW3000 driver
- DWM3001CDK board config

移除或旁路：
- Apple NIQ 主握手流程
- 对 `Libs/niq` 的强依赖

### 4.2 新增 Android OOB 模块

新增模块建议位置：

```text
Src/Apps/Src/android_ranging_tag/
```

职责：
- 解析手机发来的 OOB START_SESSION 包。
- 生成 ACK。
- 保存 pending session。
- 启动、停止、重启 FiRa responder。
- 输出启动诊断码。

第一版协议沿用当前 App 已有的 `UTOB` 包格式，必要时可调整字段，但必须保持简单、定长、可日志打印。

基础包格式：

```text
magic[4]           = "UTOB"
version[1]         = 1
msg_type[1]        = START_SESSION
payload_len[2]     = little endian
session_id[4]
controller_addr[2]
controlee_addr[2]
channel[1]
preamble_code[1]
slot_duration[2]
block_duration_ms[2]
round_duration[1]
update_rate_hz[1]
sts_config[1]
key_len[1]
session_key[16]
```

ACK 格式：

```text
magic[4]           = "UTOB"
version[1]         = 1
msg_type[1]        = ACK
payload_len[2]
status[1]
session_id[4]
```

### 4.3 BLE 接入点

第一版继续使用 QNIS：

- Service UUID: `2E938FD0-6A61-11ED-A1EB-0242AC120002`
- RX Write: `2E93998A-6A61-11ED-A1EB-0242AC120002`
- TX Notify: `2E939AF2-6A61-11ED-A1EB-0242AC120002`

改造 `Src/Comm/Src/BLE/niq/ble_niq.c` 或新增分发层：

1. 收到 BLE RX 数据。
2. 如果是 `UTOB`，交给 Android OOB 模块处理。
3. 否则可丢弃或保留原 NIQ 处理，具体看构建目标是否仍链接 NIQ。

### 4.4 FiRa responder 启动

优先复用 QANI/FIRA 已有函数和数据结构，避免重写底层 UWB。

需要完成的映射：

```text
session_id       -> FiRa Session_ID
controller_addr  -> peer/controller address
controlee_addr   -> local/tag address
channel          -> Channel_Number
preamble_code    -> Preamble_Code
sts_config       -> STS_Config
session_key      -> Static STS key/info or equivalent Qorvo field
slot/block/round -> timing params
```

如果第一轮无法完整接入 Android STS key，则先以 Static STS 调试参数跑通，并在 App 侧保持一致。

### 4.5 板端诊断

通过 QNIS Notify 给 App 返回诊断：

```text
0x0100 OOB parsed
0x0101 ACK sent
0x0110 FiRa init start
0x0111 FiRa init done
0x0120 uwbmac_start start
0x0121 uwbmac_start done
0x0130 session start begin
0x0131 session start done
```

错误码：

```text
1 BAD_LEN
2 BAD_FIELD
3 FIRA_INIT_FAILED
4 UWBMUX_START_FAILED
5 SESSION_START_FAILED
```

## 5. App 执行计划

App 可以重构，不强制保留现有结构。重构目标是让 `MyTag_test` 从“实验性单文件 BLE/UWB 管理器”变成接近 Google `UwbRanging` sample 的分层结构。

原则：

1. `androidx.core.uwb` 的使用方式优先参考 Google sample。
2. Android UWB backend 提供的参数是唯一真源；板端只跟随 App 下发的 OOB 参数。
3. BLE 代码只负责发现、连接、传输 OOB，不参与决定 UWB 参数。
4. UI 不直接拼接协议细节，而是消费状态机和 ranging result。

### 5.1 推荐目录结构

```text
MyTag_test/app/src/main/java/com/example/uwbtag/
├── MainActivity.kt
├── ble/
│   ├── BleScanner.kt
│   ├── QnisClient.kt
│   └── BleModels.kt
├── oob/
│   ├── AndroidOobPacket.kt
│   └── OobSession.kt
├── uwb/
│   ├── AndroidUwbController.kt
│   └── UwbModels.kt
├── feedback/
│   └── FeedbackManager.kt
└── ui/
    └── TagFinderScreen.kt
```

### 5.2 App 状态机

状态机参考 Google sample 的“发现对端 -> 交换 OOB -> 启动 ranging -> 消费 result”流程，并替换其中 OOB 传输层。

```text
Idle
Scanning
ConnectingBle
DiscoveringQnis
ReadyForOob
PreparingAndroidUwb
SendingOob
WaitingBoardAck
WaitingBoardStarted
Ranging
RangingOk
Failed
```

### 5.3 App 关键行为

1. BLE 扫描按 QNIS Service UUID 过滤。
2. 连接后请求 MTU 247。
3. 开启 QNIS TX Notify。
4. 创建 Android UWB controller session，流程参考 Google `UwbRanging` sample。
5. 读取 Android backend 给出的 local address 和 complex channel。
6. 从 Android UWB session 参数生成 OOB START_SESSION。
7. 写入 QNIS RX。
8. 收 ACK 和诊断。
9. 板端启动完成后调用 `prepareSession(parameters)`。
10. 从 `RangingResultPosition` 更新 UI。

### 5.4 与 Google Sample 的差异边界

保留差异：

- Google sample 使用 Nearby Connections 做 OOB；本项目使用 BLE QNIS。
- Google sample 的对端是 Android Controlee；本项目的对端是 DWM3001CDK FiRa responder。
- Google sample 的 UI 覆盖多个 demo 场景；本项目 UI 聚焦防丢器寻物。

尽量一致：

- UWB capability 检查。
- Controller session 创建。
- local address / complex channel / peer address 建模。
- `RangingParameters` 构造。
- ranging result collection。
- 错误状态和权限处理。

### 5.5 UI 第一版

只保留演示必要元素：

- 扫描设备列表
- 连接状态
- 一键开始测距
- 距离显示
- 方位箭头
- 最近 50 条诊断日志
- 失败原因

近距离反馈：
- 距离小于 1m 时手机震动
- 板端蜂鸣器暂缓，除非确认外接硬件

## 6. 暂缓内容

第一阶段不做：

- 完整 FiRa UCI over BLE GATT
- 未确认的 0x1850 BLE Service 替换
- 多 Tag 管理
- 后台常驻防丢提醒
- 蜂鸣器驱动
- 花哨 3D UI
- iOS / Apple NIQ 兼容

这些内容在真实 UWB 闭环跑通后再评估。

## 8. 主要风险与处理

### 8.1 Android UWB 参数不匹配

风险最高。处理方式：
- 所有关键参数从 Android controller session 读取。
- 板端被动跟随 App OOB 参数。
- App 和板端都打印完整 OOB 十六进制。

### 8.2 STS key / keyInfo 不兼容

处理方式：
- 第一版使用固定 Static STS 调试 key。
- App 与板端共享同一 key。
- 若 AndroidX 对 key 长度或格式有限制，再单独调整。

### 8.3 QANI 代码与 NIQ 库耦合

处理方式：
- 新建 AndroidRangingTag 工程。
- 只复用 QANI 中可独立使用的 BLE、FiRa、board、uwbmac 逻辑。
- 若去除 NIQ 后编译耦合过深，则第一版保留链接 NIQ，但入口不走 NIQ 协议。

### 8.4 DWM3001CDK AoA 能力

距离测距优先。方位角是否稳定取决于手机端 UWB 和板端天线/配置能力。

第一版验收标准：
- 距离必须可用。
- 方位角可用则显示；不可用时 UI 明确提示“当前无方向角”。

## 9. 第一阶段交付标准

完成后应具备：

1. 一个可编译的 `AndroidRangingTag-DWM3001CDK-FreeRTOS` 固件目标。
2. 一个可安装的 Android App debug APK。
3. S23 Ultra 能通过 BLE 连接 DWM3001CDK。
4. App 能发送 OOB，板端能 ACK。
5. 板端能启动 FiRa responder。
6. App 能进入 Android UWB ranging。
7. App 能显示真实距离；如果 Android 返回方位角，则显示方向箭头。

## 10. 执行顺序

实际开发按以下顺序开始：

1. 新建 `AndroidRangingTag` 固件工程骨架并保证空工程可配置。
2. 整理 App 状态机和 BLE QNIS 客户端，保证 App 可编译。
3. 固件接入 BLE OOB 分发，先实现 probe/ACK。
4. App 与固件联调 OOB 包。
5. 固件接入 FiRa responder 启动。
6. App 启动 Android ranging。
7. 修正参数兼容问题。
8. 完成 UI 和反馈。
